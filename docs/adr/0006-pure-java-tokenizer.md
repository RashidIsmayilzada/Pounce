# The Engine tokenizes in pure Java

The Engine turns text into token ids with its own small Java tokenizer (`BertWordPieceTokenizer`), read from the model's unchanged `tokenizer.json`, instead of DJL's wrapper around the Hugging Face Rust library. DJL's jar has no Windows build of that library: on Windows it tries to download `tokenizers.dll` from `publish.djl.ai`, so the Engine, which never goes online, could not start (`EngineException: Failed to load Huggingface native library`). No Maven artifact ships the missing DLL. Pure Java fixes Windows, removes a native library that could download anything on every platform, and makes tokenizing identical on macOS, Linux and Windows. ONNX Runtime stays and is now the Engine's only native library besides JNA.

The tokenizer reproduces the pipeline `bge-small-en-v1.5` declares: special tokens such as `[SEP]` matched in the raw text, `BertNormalizer` (clean text, space out CJK, strip accents, lowercase), `BertPreTokenizer`, greedy longest-match `WordPiece` with `##` and `[UNK]` for words over 100 characters, and the `[CLS] … [SEP]` template, cut to 512 tokens. Two details are copied on purpose although Java would do otherwise: the reference decides control characters, accents and punctuation with **Unicode 8.0** tables (the `unicode_categories` crate), which differ from Java 25's Unicode 16 for 618 code points, so those tables are carried over; and a text with an unpaired surrogate loses all its surrogates, as it did on its way into Rust.

## Consequences

- We own a tokenizer that supports exactly this setup: BERT WordPiece with a `BertNormalizer`, `BertPreTokenizer` and a `TemplateProcessing` or `BertProcessing` template. Loading a `tokenizer.json` of any other kind fails with "unsupported tokenizer.json". A model with a different tokenizer (SentencePiece, BPE, Unigram) means extending it.
- `BertWordPieceTokenizerGoldenTest` guards it: it compares token ids, type ids and attention mask with DJL (now a test-only dependency) for every Unicode code point, 5,000 pseudo-random mixed-script strings, hand-written cases for each tricky rule, and the texts the repository's tests and docs use: about 32,500 texts, all identical. It also requires the embeddings from both tokenizations to be bit-identical. It skips itself where DJL cannot load (Windows), and `BertWordPieceTokenizerTest` then checks a frozen fixture of 612 reference encodings without DJL.
- Speed, DJL before and pure Java after, measured on a 14-core x86-64 machine under WSL2 with JDK 25 (plain harness, not JMH; warm-up first; three runs in fresh JVMs; other builds were running, load average 5–8):
  - Tokenizing a Query (with its instruction prefix): p50 72–74 µs → 3.1–5.0 µs, p95 128–159 µs → 7–16 µs (20,000 runs each).
  - Tokenizing a Passage of about 475 tokens: 450–650 → 2,300–3,900 Passages per second.
  - Embedding, which includes the tokenizing: unchanged, because ONNX Runtime takes over 98% of the time. Interleaving both in one JVM so the load hit them equally: Query p50 7.2 → 7.0 ms and p95 17.2 → 17.2 ms (4,000 runs); 3.41 → 3.44 Passages per second (172 Passages). The absolute numbers are inflated by the load; the earlier speed spike measured on the M2 is the reference for those.
- The Engine jar shrinks from 116.3 MB to 94.8 MB: DJL's tokenizer jar alone was 18 MB, nearly all of it native libraries for three platforms, plus five Java libraries it pulled in (DJL's API, Gson, Commons Compress, IO and Codec).
